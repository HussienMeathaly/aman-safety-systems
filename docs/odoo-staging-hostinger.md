# اختبار أودو التجريبي بعد إعادة التجهيز

هذا الإجراء للنسخة `https://wahattamuyztest.odoo.com` فقط. لا يثبت جاهزية أودو الفعلي، وقد تُحذف بيانات الاختبار والمفتاح عند إعادة تجهيز النسخة التجريبية مجدداً.

## 1. حفظ المفتاح في Hostinger قبل وصول التحديث

1. افتح hPanel ← موقع osaec.sa ← Files ← File Manager، واختر الوصول لجميع ملفات الاستضافة إذا كان العرض الحالي يفتح داخل `public_html` فقط.
2. حدد مجلد `public_html` الذي يحتوي الموقع. في المجلد الأب له أنشئ مجلداً باسم `private`، لا داخله.
3. أنشئ `private/odoo-config.php` وانسخ محتوى `scripts/odoo-config.example.php` من GitHub، أو النص التالي:

```php
<?php
return [
    'url' => 'https://wahattamuyztest.odoo.com',
    'api_key' => '',
];
```

4. ضع المفتاح الجديد بين علامتي الاقتباس أمام `api_key` **في محرر Hostinger الخاص فقط**. لا تضعه في المحادثة أو GitHub أو `public_html` أو لقطات الشاشة.
5. اجعل صلاحية الملف `600` والمجلد `700` إذا كان PHP يعمل بمالك الملف نفسه؛ عند اختلاف المجموعة استخدم `640` و`750` مع المجموعة الصحيحة. لا تستخدم `777`.
6. الشكل المطلوب (المسار الحقيقي قد يختلف حسب الحساب):

```text
مجلد الموقع/
├── private/
│   ├── odoo-config.php
│   └── odoo-logs/         ينشأ تلقائياً إذا كانت الصلاحيات تسمح
└── public_html/
    ├── index.html
    ├── odoo-bridge.php
    └── odoo-client.php
```

إن منع إعداد PHP المسمى `open_basedir` قراءة المجلد الخاص، يجب السماح بهذا المسار في إعدادات الاستضافة؛ **لا تنقل المفتاح إلى public_html** للتجاوز. لا تضع نسخة فعلية من ملف الإعدادات في المشروع، حتى محلياً: ملف التجاهل هنا محمي ولم نتمكن من إضافة قاعدة له.

النشر الحالي يرفع محتويات `dist` فقط إلى `public_html`، لذلك لا يشمل مجلد `private`. تحقق من نجاح آخر تشغيل في GitHub ← Actions، ومن وجود الملفين PHP أعلاه في Hostinger. لا تعدّل وجهة النشر لتشمل مجلد `private`. إعداد النقل الحالي FTP؛ يلزم تأكيد دعم FTPS وبياناته قبل تغيير طريقة النقل. إعداد الملف الخاص لا يحتاج نقله عبر هذا النشر.

**تنبيه:** عند وصول النسخة الجديدة دون الملف الخاص سيتحول النموذج إلى واتساب؛ العميل يحتاج الضغط على إرسال. إزالة المفتاح من النسخة الحالية لا تمحوه من تاريخ GitHub: اطلب إبطال المفتاح القديم لدى مبرمج أودو. السجلات القديمة في `public_html/odoo-logs` لا تُنقل تلقائياً؛ احتفظ بما يلزم منها خارج مجلد الموقع واحذف النسخة العامة بأمان.

## 2. اختبار الاتصال والإعدادات دون إنشاء طلب

إذا كانت SSH متاحة في خطة Hostinger، فعّلها من hPanel واتصل بالطريقة المعروضة هناك؛ لا ترسل بيانات الدخول في المحادثة. انسخ `scripts/check-odoo-staging.php` إلى `private/check-odoo-staging.php` عبر File Manager. لا تضع أداة الاختبار في مجلد الموقع العام.

نفّذ الأمر التالي بعد استبدال المسار بمسار `public_html` الحقيقي من File Manager:

```bash
php /ABSOLUTE/SITE/private/check-odoo-staging.php /ABSOLUTE/SITE/public_html
```

الأداة تقرأ المفتاح من الملف الخاص ولا تعرضه، وترفض أي عنوان مختلف عن النسخة التجريبية الموثقة. نتيجة النجاح تعرض:

- `PASS: staging connection and API key.`
- `Default source`: الاسم الفعلي للمصدر.
- `Default team`: فريق المبيعات المضبوط.

قارن المصدر بما قصده المبرمج: قد يكون `Website` أو `websit` أو اسماً عربياً. لا نفترض الإملاء ولا نفرض قيمة من الموقع. اطلب منه تأكيد أن هذا هو مصدر الموقع المطلوب. عند `HTTP 401` تأكد أن المفتاح الجديد محفوظ في سجل **Lead API Clients للنسخة التجريبية**؛ إعادة تجهيزها قد تكون أعادت إعداداً قديماً. المصدر الفارغ يوقف الاختبار ويحتاج ضبطه في أودو.

## 3. إنشاء طلب تجريبي واختبار عدم التكرار

بعد تأكيد المصدر والفريق، نفّذ:

```bash
php /ABSOLUTE/SITE/private/check-odoo-staging.php /ABSOLUTE/SITE/public_html --create-test-lead
```

الأداة تنشئ طلباً باسم «اختبار ربط الموقع» دون بيانات عميل أو رقم جوال مختلق. تعيد إرساله **بنفس المرجع**، وتتحقق أن أودو يرجع رقم الطلب نفسه مع `created: false`. التشغيل الجديد ينشئ مرجع اختبار جديداً. احتفظ برقم الطلب والمرجع، لا بالمفتاح. أي تحذيرات تحتاج مراجعة سجل API داخل أودو.

افتح **أودو التجريبي** ← CRM، وابحث بعنوان الاختبار أو المرجع الظاهر. إن لم يظهر، راجع شاشة Leads وأزل مرشح «طلباتي» أو اطلب من المبرمج البحث برقم الطلب.

تحقق داخل السجل:

- الطلب موجود مرة واحدة، والوصف العربي سليم.
- في معلومات التتبع/التسويق (قد يختلف اسم التبويب)، حقل **Source / المصدر** يشير إلى الموقع كما أكد المبرمج.
- فريق المبيعات صحيح، والمسؤول يطابق الإعداد المتفق عليه؛ قد يكون غير معيّن عن قصد.

الواجهة المتاحة لا تسمح بقراءة الطلبات، لذلك عرض مصدر الاتصال الافتراضي وحده ليس إثباتاً لمصدر الطلب المحفوظ: يلزم فحص السجل في CRM. يمكن أرشفة سجلات الاختبار يدوياً بعد الانتهاء.

## 4. اختبار نموذج الموقع نفسه

بعد نجاح ما سبق، افتح https://www.osaec.sa/ وأرسل طلباً باسم واضح «اختبار ربط الموقع»، برقم جوال تملكه أو رقم اختبار يحدده المبرمج، ووصف فريد مثل «اختبار النسخة التجريبية بعد إعادة التجهيز — وقت الاختبار ...».

تحقق من ظهور رسالة نجاح **وليس فتح واتساب**، ثم ابحث عن الطلب في أودو التجريبي وافحص المصدر والجوال والوصف. أعد نفس البيانات مرة واحدة للتأكد أنه لا ينشئ طلباً آخر. لا تستخدم بيانات عميل حقيقي، ولا تغيّر الوصف في إعادة المحاولة.

إذا لم تتوفر SSH، يمكن اختبار نموذج الموقع مباشرة بعد إعداد المفتاح، لكن اختبار `ping` يحتاج تشغيل الأداة من المبرمج عبر Hostinger أو جهازه الآمن؛ لا ننشئ صفحة اختبار عامة ولا نضع المفتاح في المتصفح. ظهور المصدر داخل CRM يظل مطلوباً.
